## 1. State of the tree

### What it is

A dependency-free stdio MCP client for Roblox Studio, in two full
implementations sharing one surface:

| | Python | Node |
|---|---|---|
| entry | `python/src/roblox_studio_mcp/extended_server.py` (1,627 L) | `node/src/extendedServer.ts` (1,398 L) |
| transport | `client.py` (425 L) | `client.ts` (406 L) |
| wrapper | `roblox.py` (428 L) | `roblox.ts` (472 L) |
| extended modules | 15 files under `python/src/roblox_studio_mcp/extended/` | 17 files under `node/src/extended/` |
| tests | 33 files, `python/tests/` | 20 files, `node/tests/` |

170 files in the tree excluding `node_modules`, `.git`, `__pycache__`,
`.mypy_cache`, `.pytest_cache`, `dist`, `*.egg-info` (counted by shell). It
also serves 7 `skills/rsx-*.md` documents through `extended_skill`, loaded by
directory walk from the repo root so both implementations read one copy
(`python/src/roblox_studio_mcp/extended/skills.py:99-116`,
`node/src/extended/skills.ts:76-86`).

### How parity is enforced

Two generated contracts, each asserted by both suites:

- **`parity/tools.json`** — generated by `parity/build_contract.py` from the
  *Python* server's `_EXTENDED_TOOLS` (`build_contract.py:157-184`). Compares,
  after `_normalise_schema` (`build_contract.py:123-154`): tool names, property
  names, JSON types, `items_type`, `has_default`, `enum`, `required`, the
  `read_only` hint, per-tool description length, total description length, and
  the `steers` table. Asserted by `python/tests/test_parity.py` and
  `node/tests/parity.test.ts`.
- **`parity/errors.json`** — error codes and **exact message wording** for
  `unknown_arguments`, `handlers`, `sites`, and
  `deliberately_not_argument_faults`. Asserted by
  `python/tests/test_error_parity.py` and `node/tests/error-parity.test.ts`,
  both driving probes through the *real* code
  (`test_error_parity.py:353-363`, `error-parity.test.ts:265-272`).

Beyond the contracts, three properties are asserted that the contracts cannot
express, and these are the genuinely good parts of this codebase:

1. **Closed-set exhaustiveness** — every declared error code has a producer and
   every raised code is declared, with a **known-present control** so the scan
   cannot pass vacuously (`test_closed_sets.py:200-208`:
   `self.assertIn(E.INVALID_ARGUMENT, found)` +
   `assertGreaterEqual(len(found), 3)`; mirrored at
   `node/tests/errors.test.ts:198-203`). This is what found `LAUNCH_FAILED`
   being unreachable.
2. **Action-set exhaustiveness** — every advertised `action` enum value is
   handled, not merely accepted (`test_closed_sets.py:237-275`).
3. **Unknown-argument refusal before dispatch**, on both sides.

### What parity does NOT catch — the useful part

- **Behaviour.** `test_parity.py:24-26` says so outright: wording and internals
  are not compared. Two servers can pass every gate and return different
  answers to the same request. Section 2's first finding is exactly this.
- **The `errors.py` pattern table.** `node/src/extended/errors.ts:70-76`
  documents the precedent in a comment: `LAUNCH_FAILED` was missing from Node's
  table, so *every launch failure* classified as `UNKNOWN` on Node and
  `LAUNCH_FAILED` on Python. Neither contract sees this — it is a list of
  strings, not a schema. It was found by hand, and nothing prevents it recurring.
- **`STEERS` on the Node side.** `extendedServer.ts:34-38` claims all three
  copies are "asserted equal by both suites". Python's is
  (`test_parity.py:52-89`). **Node's is not** — see 2.3.
- **Dead code.** Nothing asserts that a module is reachable from the server.
  2,195 lines of Node source are unreachable — see 2.2.
- **`skills/`.** `TODO.md:3080` already records "untracked and the repo has no
  CI over it". Confirmed by reading `.github/workflows/ci.yml` (72 lines): both
  jobs run only `python/tests` and `node/{typecheck,build,test}`. No job reads
  `skills/`, `parity/` scripts, or `docs/`.
- **Return *shapes*, only partly.** `parity/errors.json` pins error payloads
  exactly. *Success* payloads are pinned nowhere. `extendedServer.ts:1004-1009`
  documents having shipped `rawBytes`/`savePath` where callers were promised
  `raw_bytes`/`save_path` — that was found by hand and is a parity hole that
  remains open.
- **`skills/` vs code.** `skills.py` validates frontmatter shape only
  (`skills.py:135-137`), never that a skill's claims match the implementation.
  `TODO.md:3082-3086` records 640 classes / 50 methods / stale numbers as
  unsourced. Confirmed structurally, not individually.

## 2. Real defects found in this pass

Ordered most severe first. Four findings; I did not pad.

### 2.1 `node/src/extendedServer.ts:960-966` — `action=stop` throws `NO_STUDIO` on every call, on both implementations' data shape. **SEVERITY: HIGH.**

```ts
const raw = await (client as unknown as {
  callTool(name: string, args: Record<string, unknown>): Promise<unknown>;
}).callTool("list_roblox_studios", {});
const studios = Array.isArray(raw) ? (raw as Array<Record<string, unknown>>) : [];
if (studios.length === 0) {
  throw new Error("no Roblox Studio instances are connected");
}
```

**What breaks.** `MCPClient.callTool` returns `Promise<CallToolResult>`
(`node/src/client.ts:276`), and `CallToolResult` is a class instance
(`node/src/types.ts:120-131`), not an array. `Array.isArray(raw)` is therefore
**always false**, so `studios` is **always `[]`**, so line 965 **always**
throws. `action=stop` is unreachable beyond the `studio_id` presence check at
`:859`.

`errors.ts:52` maps `"no roblox studio instances are connected"` → `NO_STUDIO`.
So the caller is told **no Studio is attached** when one is. That is the exact
failure class this project exists to prevent: a confident, wrong, actionable
answer. It sends the caller to check the MCP toggle
(`roblox.ts:245-248` names this failure mode as the reason for its own
care).

**This is a regression of a bug already found and fixed in the same file.**
`guardScreenCapture` at `:89-95` does it correctly and carries the comment:

> `.json()`, not the raw result: `callTool` returns a CallToolResult, and an
> earlier version of this read it as a bare array. That produced a nonsense
> candidate list rather than an error, which is the worst shape for a guard.

`extendedServer.ts:824-828` (`action=list`) does it correctly a third way, via
`JSON.parse(rows.text())`. So three call sites of `list_roblox_studios` exist;
two are right and one is wrong. `node/src/roblox.ts:250-251` is also correct.

**Realistic trigger.** Any `extended_manage_instance {action: "stop",
studio_id: X}` on the Node server. Always. Node's `action=stop` is described in
three places as *refusing only when >1 Studio is attached*
(`IDENTITY.md:21`, `extendedServer.ts:21`, `instance.ts:10-12`); it in fact
refuses always.

**Control for the negative claim** (no test would catch it): grepping
`node/tests/*.ts` for `resolvePid|'stop'|stopProcess|manage_instance` returns
**2 hits**, both in `error-parity.test.ts` and both checking the *schema enum*
(`error-parity.test.ts:466`) and a comment (`:475`) — not behaviour. The same
filter returns 2 hits for `manage_instance`, so the filter works.

**Severity HIGH** because the action is irreversible-adjacent (it terminates a
process), it is the only way to stop a Studio from Node, and it currently
reports a Studio as absent.

**Not fixed by wiring in `logid.ts`** — see 2.2. The one-line fix is
`const studios = (raw as CallToolResult).json()`, matching `:90`.

### 2.2 `node/src/extended/logid.ts` (1,908 L) + `locks.ts` (287 L) are complete, tested, and **imported by nothing in `src/`.** **SEVERITY: HIGH (dead code + wrong error text).**

positive control:

| `locks\.js\|logid\.js` | **0 hits** | 2 hits (`locks.test.ts:34`, `logid.test.ts:61`) |
| exported symbols `liveIdentities`, `matchMeshName` outside `logid.ts` | **0 hits** | — |
| control symbols `parseIdentity` / `listStudioProcesses` / `readInBandIdentity` | 3 / 3 / 5 hits | — |

The full import statement list for all of `node/src` (dumped by shell) contains

**Why it matters, beyond tidiness.** `IDENTITY.md:18`, `:50-55`, `:72` all

### 2.3 `node/src/extendedServer.ts:34-38` — the docstring claims Node's `STEERS` is asserted against the contract. It is not. **SEVERITY: MEDIUM.**

```ts
 * `python/src/roblox_studio_mcp/extended_server.py` and `_STEERS` in
 * `parity/build_contract.py`; all three are asserted equal by both suites,
 * because a drift here is a model quietly using the worse tool forever and
 * nothing anywhere reports it.
```

Only **two** copies are asserted. `python/tests/test_parity.py:52-89` compares
`build_contract._STEERS` against `extended_server._STEERS` byte-for-byte, plus
two structural checks. Nothing compares Node's.

**Control.** Grepping all of `node/` for `STEERS|steers|NOTE: prefer` returns
**11 hits**. Two are the definition (`extendedServer.ts:40-51`), one is the use
site (`:1332`), and the only test hit is `improvements.test.ts:604-634`, which
asserts the appended description **contains** `"prefer extended_"` — a substring
check, not equality, and it iterates `Object.keys(STEERS)` so it can only ever
confirm the table is self-consistent. It never opens `parity/tools.json`
(`error-parity.test.ts:102` and `parity.test.ts:55` show the pattern those files
*do* use when they mean to read the contract).

**What breaks.** Edit a steer in `build_contract.py` or on the Python side and
regenerate: Python's test is the only thing that notices, and Node's copy keeps
the old note. Per the docstring's own reasoning, a model on the Node server is
then silently steered toward the worse tool, permanently, and every call still
succeeds. Today the two copies happen to be identical — I read both
(`build_contract.py:67-95` vs `extendedServer.ts:40-51`) and they match — so this
is a latent hole, not a live wrong answer. **Reported as a defect in the
enforcement, not in the data.**

### 2.4 `python/src/roblox_studio_mcp/extended/locks.py` (179 L) is imported by no source file on either side. **SEVERITY: MEDIUM.**

Grepping all of `python/src/roblox_studio_mcp` for
`^\s*(from|import)\s+.*\blocks\b` returns **zero hits**, while the same filter
for `logid` returns 19 (including the live call sites
`instance.py:793, 969, 987, 1009, 1058`). `locks.py` is referenced only by
`python/tests/test_locks.py` and `test_platform_macos.py:26`. Its Node twin
`locks.ts` has the identical status (2.2).

`locks.py` is the `.lock`-file PID join — `IDENTITY.md:26-32` describes it as
the cheaper alternative to the log chain. It is not on the request path of
either server. This is `find_unused_python.py`'s own category 2
("test-only", `find_unused_python.py:6-8`), correctly classified by a script that
nobody appears to have run against this file since it landed. **Not a runtime
defect.** It matters because it inflates the "1,012 lines of debt" figure that
drives the port/no-port decision (see 3.1).

## 3. Docs that contradict the code

Beyond the four items already on record. I found **three**.

### 3.1 `AGENTS.md:20` and `:82-87` — the port gap is described as 1,012 lines. Two of them are already written. **HIGH.**

`AGENTS.md:20`: "that is how this project acquired 1,012 lines of debt, and the

The *behavioural* claim is true — Node's `action=stop` genuinely cannot resolve
a `studio_id` on a multi-Studio machine. The *factual* claim about what exists
on disk is false, and it is the claim that tells a maintainer how much work
remains.
